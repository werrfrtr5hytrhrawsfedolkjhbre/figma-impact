# DSH 变更影响分析 · M0（依赖图）

只读的 Figma 本地插件。**M0 只做一件事：把文件的依赖关系抽成图，并在面板里回答「谁依赖它 / 它依赖谁」。**

不联网、不调 AI、不修改画布。

## 四类边

| 类型 | 来源 | 用途 |
|---|---|---|
| `prototype` | `node.reactions` → `destinationId` | 页面跳转链路，自动建图（不用手工标注） |
| `instance` | `getMainComponentAsync()` | 组件 → 实例的传播路径 |
| `style` | `textStyleId` / `fillStyleId` / `strokeStyleId` / `effectStyleId` | 样式引用（库样式也能拿到 id） |
| `child` | 图层树 | 仅用于定位，不参与影响计算 |

样式读的是**节点上的引用**，不是 `getLocalTextStylesAsync()` 的列表——所以远程（库）样式同样能建边。

## 导入

与量尺插件相同：

1. Figma 桌面端打开目标文件（Design 文件，不能是 Figma Sites）
2. 左上角 Figma 图标 → **Plugins → Development → Import plugin from manifest…**
3. 选本目录的 `manifest.json`
4. 之后从 **Plugins → Development → DSH 变更影响分析** 启动

## 使用

打开即自动扫描。面板三个标签：

- **页面跳转** —— 原型连线清单，点一行可以在画布上定位到目标节点
- **组件使用** —— 按主组件分组，列出每个组件的实例
- **上下游** —— 选中任意节点后，显示「谁依赖它」（上游，最多 3 跳）和「它依赖谁」（下游，最多 3 跳）

**导出 JSON** 会把整张图复制到剪贴板，方便排查或后续喂给 AI。

## 预期结果（按已测数据）

在「模板复制到 Design」的那份文件上，应该看到：

- 节点 ≈ 1,293
- 原型跳转 ≈ 56
- 组件实例 ≈ 18
- 样式引用 > 0（如果样式确实被应用了）

## 已知限制

- **实例内部不展开**（`skipInvisibleInstanceChildren = true`）。选中实例内部的子节点时，「上下游」会提示不在图里。
- 样式边只有 id，还没有解析成样式名——M0 不关心，M1 再补。
- 跨文件的组件（团队库里的主组件）`getMainComponentAsync()` 可能返回 null，这类实例暂时没有 `instance` 边。
- 图每次打开重算，不缓存。当前规模（1,300 节点 / 45ms）不需要缓存。

## M1：影响分析 + 画布标记

选中一个节点 → 点 **直接影响 / 间接影响 / 潜在影响** → 从它出发沿「组件 ↔ 实例」「画板 ↔ 跳转」双向展开，按跳数分三级：

| 等级 | 颜色 | 含义 |
|---|---|---|
| 1 跳 | 红 | 直接影响 |
| 2 跳 | 橙 | 间接影响 |
| 3 跳 | 黄 | 潜在影响 |

**一次分析算出全部三档**，三个按钮是列表的**视角切换**（不重算、不叠加）；再点一次当前按钮回到「全部」。画布始终标出全部等级，方便看完整连锁地图。

画布上的标记全部画在一个 overlay 容器里（`[DSH] impact · <sessionId>`），**不改动原节点任何属性**：

- 每个受影响节点一个描边框：外扩 4px、描边 4px，彩色带落在节点外侧 4~8px，避免被 Figma 的选中蓝框盖住
- 画布上会生成**两个普通图层**，都在页面顶层、都可被任何人操作：
  - `[DSH] 影响范围 · <session>` —— 描边框 + 编号，始终显示
  - `[DSH] 建议气泡 · <session>` —— 编号 + 建议文字，**协作者不开插件也能用图层眼睛隐藏**
- 左上角一个**编号 + 建议气泡**：宽度随文字收缩（最宽 200px，超出自动换行），最多 36 字；黄色档用深色字保证对比度
- 面板上的「显示建议气泡」勾选框是给插件使用者的快捷方式（重绘时决定要不要生成建议气泡层）
- 气泡是 overlay 里的独立图层，绝对定位，**不进入原节点、不改任何尺寸/位置/样式/布局**；节点贴着画布顶部时气泡自动翻到下方
- 点 **清除标记** 一键删除容器，设计稿回到原样

面板「影响」栏按等级列出条目，点一行可定位；顶部状态栏给出「直接 / 间接 / 潜在」计数。

### M1 的已知限制

- **标记是快照**：移动节点后框不会跟着走，重新分析一次即可（M2 接 `documentchange` 做实时跟随）。
- 超大容器（任一边 > 20000px）跳过不画，避免糊满画布。
- 实例内部节点（`I1:...`）可以被标记，但它们在依赖图里没有出边。
- 跳数枚举是**双向**的：既算「它影响谁」也算「谁影响它」，因为组件与实例的依赖方向相反，单方向会漏。
- 会话摘要写到 `figma.root` 的 `dsh:lastSession`（插件数据，随文件同步），供后续多人协作使用。

## M2：AI 语义定位（DeepSeek）

面板里展开 **AI 分析（DeepSeek）**：

1. 粘贴 DeepSeek API Key → **保存**（存 `figma.clientStorage`，只在本机，不进文件、不进代码）
2. 写一句变更描述，例如「把品牌主色从橙色改成深蓝」
3. 点 **AI 分析影响**

### 分工（关键设计）

| 步骤 | 谁做 | 原因 |
|---|---|---|
| 把文档压成「区域清单」（id + 类型 + 名称） | 代码 | 控制篇幅、保证 id 真实 |
| 判断哪些区域受影响、分几级、为什么 | DeepSeek | 语义理解是它的活 |
| 校验 id 是否真实存在 | 代码 | **防幻觉**：模型编的 id 直接丢弃 |
| 组件区域 → 展开它的实例 | 代码 | 图关系是确定性的，不该让模型算 |
| 画标记、计数、写会话摘要 | 代码 | — |

模型只负责「语义定位」，节点展开由图算法负责——这是这类工具能落地的前提。

### 已知限制

- 模型只能从**区域清单**里选（每页最多 24 个顶层 + 每个区块 10 个二级），更深的节点不在候选里。
- 单次最多选 12 个区域；组件类区域会额外带上它的实例。
- `networkAccess` 已放行 `api.deepseek.com`；离线或 Key 无效会在状态栏报 HTTP 错误。
- 每次分析 = 一次模型调用（约 2~4k 输入 token），不缓存。
- 改 Key：重新展开保存即可。

## M3：评审状态机

```
IDLE ──开始评审──▶ REVIEWING ──发起者结束──▶ SETTLING ──▶ IDLE（带结算报告）
```

| 阶段 | 行为 |
|---|---|
| `IDLE` | 正常分析 |
| `REVIEWING` | **分析冻结**（影响 / AI 按钮禁用）；`documentchange` 只记录、不重算 |
| `SETTLING` | 对账：标记节点被改了没有、有没有改到未标记的节点 |

### 会话存在哪

`figma.root` 的插件数据 `dsh:review`，随文件同步。所以：

- 张三点了「开始评审」，李四打开插件会看到「评审中 · 张三」，按钮直接是禁用状态
- 换设备、重开 Figma 都还在

### 谁能结束

只有发起者：结算前比对 `figma.currentUser.id` 与记录里的 owner。别人的「结束评审」按钮是灰的（`title` 会说明原因）。

> `figma.currentUser` 需要 manifest 里的 `"permissions": ["currentuser"]`。**改过 manifest 要重新导入一次插件。**

### 结算报告

- **被修改**：标记节点里指纹变化了的（逐个列名字，可点定位）
- **未改动**：标记了但没人动
- **已被删除**：标记节点被删了（孤儿）
- **越界改动**：评审期间被改、但**不在标记范围内**的节点 —— 这是评审最容易漏掉的一类

### 两条口径（重要）

1. **改动记录依赖"有人在开着插件"**。插件关掉时发生的编辑不会进 `documentchange` 日志；但标记节点的改动在结算时靠**指纹对账**兜底，不会漏。
2. **越界审计只覆盖日志**。插件全程没开的话，越界改动查不到——文档里会写明这个限制。

### 跨页

| 环节 | 跨页支持 |
|---|---|
| 扫描 / 建图 | ✅ 遍历 `figma.root.children` 全部页面 |
| 影响分析 | ✅ 图里包含跨页的原型跳转与组件实例 |
| 画布标记 | ✅ 按「节点所在页面」分别建 `[DSH]` 图层，标记落在各自页面上 |
| 评审记录 / 结算对账 | ✅ `getNodeByIdAsync` 跨页取节点 |
| 点击列表定位 | ✅ 自动 `setCurrentPageAsync` 切到目标页 |

### 关闭面板会自动清理标记
`figma.on('close')` 触发时删除 `[DSH]` 开头的两个图层，画布恢复原样，不留垃圾。

例外：**评审进行中**关掉面板，标记虽然会被清，但重开插件时会根据 `dsh:review` 里记录的节点 id / 等级 / 理由**自动重建标记**，评审可以接着做。

> 如果 Figma 崩溃或被强制结束，`close` 可能不触发；此时手动删掉图层面板里 `[DSH]` 开头的两个图层即可，或重开插件点「清除标记」。

## M4：一键应用修改建议

AI 不再只给文字建议，而是给出**可执行的修改指令**，校验通过后由插件批量执行。

### 三种可执行操作

| kind | 作用 | 例子 |
|---|---|---|
| `text` | 改文本内容 | 「已开启」→「已关闭」 |
| `variant` | 改实例的变体属性 | `State=On` → `State=Off` |
| `visible` | 改显隐 | `true` → `false` |

其他任何操作都会被拒绝——插件的写能力只到这一步，不做「AI 随便改画布」。

### 四道护栏

1. **白名单**：只接受上面三种 `kind`
2. **id 校验**：节点必须存在于本次清单
3. **`from` 比对**：当前值必须等于模型说的旧值，否则拒绝（防止模型记错，也防止你中途手改过）
4. **撤销**：批量执行后调用 `figma.commitUndo()`，**一次 Ctrl+Z 撤销整批**

> 不加 `commitUndo()` 的话，插件改动默认**不进撤销历史**，用户按 Ctrl+Z 是撤不掉的。这行是关键。

### 失败处理

没通过校验的条目仍然显示在列表里，但置灰并标注原因（「当前文本与建议的 from 不一致」「实例没有变体属性 State」等），不会被执行。

应用阶段也可能失败（比如混合字体不能改 characters），失败的逐条回报，成功的照常生效。

### 组件本体 → 自动展开成实例

变体属性只存在于**实例**上：组件本体（COMPONENT）和组件集（COMPONENT_SET）没有可写的变体值。

所以当模型把变体改动指到组件本体时，插件会：

1. 取该组件（或组件集下全部变体）的所有实例
2. 逐个按同样规则校验（属性是否存在、当前值是否等于 `from`）
3. 通过校验的**每个实例各生成一条指令**

这样「把开关默认值改为关」就会展开成「所有开关实例切到 Off」，而不是卡在无法执行的本体上。

如果该组件在文件里根本没有实例，会明确提示「这个组件目前没有任何实例」——这时确实没有可应用的东西。

### 清单为什么带主组件名

实例行会附带 `主组件: 「Switch」`，模型才能判断"哪些实例属于我要改的那个开关"。同时实例内部的文本（id 以 `I` 开头）会排在文本清单前面——状态文案通常就藏在实例里。

### 布尔属性（开关默认值）

开关的「默认值」通常是**布尔组件属性**（`Property 1(BOOLEAN)=true`），不是变体。M4 现在同时支持：

| kind | 适用属性类型 | 值 |
|---|---|---|
| `variant` | `VARIANT` | 变体名（字符串） |
| `boolean` | `BOOLEAN` | `true` / `false` |

清单里每个属性都带类型标注（`属性: Property 1(BOOLEAN)=true; State(VARIANT)=Default`），模型据此选对 kind。`boolean` 指到组件本体时同样会自动展开成所有实例。

### 应用后怎么核实

1. 应用完成后**自动跳到第一处改动**的节点（切换页面 + 选中），右侧面板直接看属性值
2. 列表里每条显示「已应用 · 现为 `<实际读回的值>`」——不是回显你填的目标值，而是**改完后重新读一次**
3. **点列表条目的文字**可跳到画布上那个节点，逐条核对
4. 不满意按一次 **Ctrl+Z**，整批回滚（`commitUndo` 把这批合成一步）

### 清单怎么找 BOOLEAN 实例

不再依赖依赖图里被截断的实例列表，而是**单独全量扫描**：遍历每一页的 `findAllWithCriteria({types:['INSTANCE']})`（扫描期间临时关掉 `skipInvisibleInstanceChildren`），逐个读 `componentProperties`，把带 `BOOLEAN` 属性的实例单独成节，最多 60 个。

面板「建议」栏顶部会显示模型实际看到的数量：

```
模型看到的清单：布尔实例 6 · 其它实例 40 · 组件集 4
```

如果布尔实例是 `0`，说明这个文件里**真的没有实例暴露 BOOLEAN 属性**——那"默认值"就不在实例上，而在组件定义里（`componentPropertyDefinitions`），需要另一套改法。

### 修改范围（scope）

「生成修改建议」多了一个范围选择，默认 **仅选中节点**——因为变更通常是"改我选的这个东西"，不是"改整个文件"。

| 范围 | 含义 |
|---|---|
| 仅选中节点（默认） | 只允许改锚点及其内部元素；其余建议会保留但标灰「超出本次范围」 |
| 同组件的所有实例 | 锚点所在组件的全部实例 |
| 整个文件 | 全文件检索 |

没选中节点时会自动退化成「整个文件」，提示栏会写明。

### 锚点是怎么给模型的

选中的节点会作为 `【本次变更的锚点】` 放在清单最前面，直接列出**这个节点自己的** `componentProperties`（带类型和当前值）和它内部的短文本，例如：

```
【本次变更的锚点】只在这个范围内改
- 「Component 34」 type=INSTANCE id=1:23  主组件:「Component 31」
  属性: Property 1(BOOLEAN)=true
  内部文本：
  - 内部文本「已开启」 id=I1:23;4:5
```

这样即使全局扫描没找到（比如实例在别的结构里），锚点自身的属性也一定在模型眼前。

### 相关范围（默认）

只改锚点太窄、全文件太散，所以默认范围是 **锚点 + 相关范围**：

| 收进来 | 目的 |
|---|---|
| 锚点本身与内部文本 | 直接改这个开关 |
| 锚点所在页面上的其它实例、文本 | 同一屏/同一页里的关联开关、文案、提示 |
| 同一组件的全部实例（跨页） | 「所有这个开关」这类改动 |

候选池由代码按位置和组件关系圈定，**具体挑哪些由模型按语义判断**；用户再逐条勾选。

范围外的建议不会被丢掉，而是标灰「超出本次范围」，方便对照"AI 想改什么、我允许到什么程度"。

> 注意：候选池的"相关"是按 **Figma 页面** 划分的。如果相关界面被拆在不同的 Figma 页面里，需要切到「整个文件」范围。

### 建议必须建立在影响分析之上

之前 M4 自己按页面重新捞了一遍候选，和影响分析是两套清单，导致"建议"和画布上的红橙黄标记对不上。

现在改成一条链路：

```
影响分析（图传播 + AI 语义）
   └─ 得到受影响的节点集合（带等级与理由）
        └─ 生成修改建议：只在这个集合里挑能改的
             └─ 逐条校验 from → 勾选 → 应用 → 可整批撤销
```

- 有影响分析结果时：候选池 = 影响集合，提示栏显示「基于影响分析（N 个节点）」，范围选择不再生效
- 没有影响分析时：才退回按范围盘点（并提示「未做影响分析，按所选范围盘点」）

建议栏顶部会写明候选来源：`候选来自影响分析：N 个节点（与画布上的标记同一批）`。

### 撤销之后状态不对怎么办

Figma 的 Ctrl+Z 对插件改动只有一步（靠 `commitUndo()` 合成），一旦出现"只撤回了一部分"，画布状态和你的预期就不一致了——而建议是根据**当前实际值**生成的，于是会出现"只有锚点还有建议、其它节点被认为已经改好了"。

两个工具解决：

| 按钮 | 作用 |
|---|---|
| **核对现状** | 逐个读回影响集合里每个节点的当前值（变体/布尔/文本/显隐），点条目可跳到画布 |
| **回滚本次应用** | 用插件记录的 `from` 精确恢复，**不依赖 Figma 撤销栈**，整批还原 |

另外：分析之后文档若又发生改动（撤销也算），建议栏会提示"文档又变了，建议先重新分析"。

### 两条分析路径的关系

| 入口 | 方法 | 特点 |
|---|---|---|
| 直接影响 / 间接影响 / 潜在影响 | 图传播（原型跳转 + 组件实例边） | 确定性、不联网、只能找到结构上连着的 |
| AI 分析影响 | 图传播 ∪ 语义检索 | 能补上"功能相同但结构不相连"的节点 |

旧版 AI 分析会**替换**图结果，导致两个入口给出不同清单、建议候选池也随之不同。

现在 AI 分析把当前选中节点的图传播结果**并进来**（`source` 标注 `图` / `AI` / `图+AI`），因此：

- 同一个锚点：AI 结果 ⊇ 按钮结果
- 建议候选池 = 当前影响集合，两个入口只差在"AI 补了多少"

### 为什么改成"图约束 AI"

早期版本让 AI 从文档摘要里挑"影响区域"，等于让模糊的一方决定"是谁受影响"。问题是：

- 语义召回不可验证：FAQ、帮助页都可能被当成"相关"
- 两个入口（按钮 / AI）产出两套清单，建议的候选池随之漂移

现在的分工：

| 角色 | 负责 | 可验证性 |
|---|---|---|
| 图传播 | 决定**哪些节点受影响** | 每条都能说清是哪条边（跳转 / 实例） |
| 结构扩展 | 补同一容器内的兄弟节点 | 规则固定：同一个父节点下 |
| AI | 给每个受影响节点**写一句说明** | 只能标注已有 id，编造的会被丢弃 |

AI 的输出不再包含新节点：它返回 `reasons: [{id, why}]`，id 不在影响集合里就丢弃。这样"是谁"永远可解释，"为什么"才交给模型。

### 三个视角按钮 vs AI 分析

| 操作 | 结果 |
|---|---|
| 直接影响 / 间接影响 / 潜在影响 | **只显示图传播**的结果（理由来自边：跳转 / 实例 / 同容器） |
| 先点视角按钮，再点「AI 分析影响」 | 在同一视角上**追加**「AI·」语义说明，不改变条数 |
| 直接点「AI 分析影响」 | 展示三层全部图传播 + 语义说明 |

同一份影响集合（`computeImpact(锚点, 3)`）只算一次，视角按钮只是过滤器；AI 只往每条上追加 `aiWhy`，不覆盖图理由、也不增删节点。

### 修改建议的候选池为什么稳定

「生成修改建议」不再读取界面上的列表状态，而是**用根节点重新算一遍影响集合**（`impactRootId` → `computeImpact(rootId, 3)`），再交给模型挑。因此：

- 点哪个视角按钮、有没有跑过 AI，候选池都一样
- 模型温度固定为 0，同样输入下输出更稳定

界面状态只影响"你看到哪一层"，不影响"建议基于什么"。

### 回到锚点

分析之后，点列表里的条目只是**查看**（会改变画布选中），不会改变锚点。工具栏新增「回到锚点」，一键选回本次分析的根节点。

同时：当当前选中的节点属于影响集合时，再点「直接影响/间接影响/潜在影响」只切换视角、不会以它为新锚点重算；状态栏会提示「锚点仍是 X」。

### 气泡里显示 AI 说明

画布气泡的文案 = `图理由 · AI：语义说明`，例如：

```
#3  它跳转到这个画板 · AI：开关默认值变了，这个状态文案要同步
```

宽度上限从 200px 提到 240px，超过 60 字截断。AI 说明只有在跑过「AI 分析影响」之后才会出现（标记是在分析时画的）。

## 面板布局（v2）

```
┌ 当前选中：xxx ────────────────────────────┐
[影响节点显示] [AI 影响分析]     [影响节点修改建议]
┌ 变更描述（一句话） ───────────────────────┐
☑ 显示建议气泡
范围 [选中节点 + 相关范围 ▾]
[回到锚点] [清除标记]
▸ AI 接入            ← 只有 Key 输入 / 保存 / 测试
```

| 控件 | 行为 |
|---|---|
| 影响节点显示 | 只跑图传播（确定性），一次算出三层 |
| AI 影响分析 | 同一份图传播 + AI 语义说明；未接入 AI 时禁用 |
| 影响节点修改建议 | 固定在最右；基于影响集合生成可执行的修改指令 |
| 影响栏目 | 子栏目「全部 / 直接 / 间接 / 潜在」切换显示，不重算 |
| AI 接入 | 折叠面板，只放 Key（后续可换 GPT 等模型） |

设计意图：**分析、解释、修改**三件事各占一个按钮，AI 只出现在需要它的两处；Key 这类配置收进折叠区，不占主流程。

### 子栏目联动画布

切换「全部 / 直接 / 间接 / 潜在」时，画布标记同步重建（`redraw` 消息，不重新分析）：

- 只保留当前等级的描边框、编号和建议气泡
- 切换到没有节点的等级时，画布清空为一个空的 `[DSH]` 图层（不丢数据）
- 「显示建议气泡」勾选框的重绘也走同一份过滤结果，两者不会打架

### 变更描述历史

「变更描述」右侧有一个「历史 ▾」按钮，展开最近 **6 条**用过的描述（去重、置顶），点一条直接填回输入框。

- 存储：`figma.clientStorage` 的 `dsh:changeHistory`，只存本机
- 记录时机：AI 影响分析成功、修改建议生成成功（失败的不记）
- **自动清空**：应用完全部变更后、评审结算后，输入框清空，内容仍在历史里

### 基础属性也可改（P0 + P1 + P2）

在 `text / variant / boolean / visible` 之外，新增六类可执行修改：

| kind | 作用 | from / to 格式 | 前置条件 |
|---|---|---|---|
| `fill` | 纯色填充 | `#RRGGBB` | 节点第一个填充是 SOLID |
| `opacity` | 不透明度 | 0~1 数字 | — |
| `radius` | 圆角 | 数字（px） | 非混合圆角 |
| `font` | 字号 / 行高 | 数字，需 `property: fontSize \| lineHeight` | 文本节点且非混合字体 |
| `size` | 宽高 | `"320x48"` | 可 resize 的节点 |
| `spacing` | auto-layout 间距 | 数字，需 `property: itemSpacing \| paddingTop ...` | 节点是 auto-layout 容器 |

清单里每条对象会多一段 `可改: fill=#FFFFFF; radius=8; size=320x48`，只有列出来的属性才会被模型使用。

校验规则与文本一致：**当前值必须等于 `from`**（数值容差 ±0.5，颜色忽略大小写）。应用失败逐条回报原因（实例内部不可写、混合字体、不是 auto-layout 等），成功后仍是一次 `commitUndo()` 整批可撤销。

`position`（x / y）按约定不做：auto-layout 会覆盖位置，收益低、破坏性高。

### 文本改动的两个关键放宽

1. **支持局部替换**：`text` 的 `from` 不必是整段文本，只要是当前文本里真实存在的片段即可（`node.characters.replace(from, to)`）。这让「把句中的『工序性』改成『工序』」这类指令可用。
2. **长文本不再被跳过**：清单里超过 60 字的文本会显示开头并标注字数，改局部时用片段或 `range`。

### 字体

- `font` 现在支持 `property: "fontName"`，格式 `Family|Style`（如 `Inter|Bold`）
- 换字体只加载**目标字体**，原字体缺失也能换
- 中文名做别名映射（宋体→SimSun、黑体→SimHei、微软雅黑→Microsoft YaHei…），失败再按可用字体列表模糊匹配
- 只想改句中一个词时加 `"range":"那个词"`，走 `setRangeFontName`，不影响整句
